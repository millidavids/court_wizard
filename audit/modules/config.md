## config

**Scope:** `src/config/` — game configuration, save data, input bindings, disk persistence, and legacy migration.

---

### Mental Model

The config module is the game's entire persistence layer: one plugin (`ConfigPlugin`) registers a tight debounce-and-flush lifecycle. At startup, settings are loaded from a TOML config file and applied to Bevy's `Window` component and a `GameConfig` resource. Save data lives in a separate unified save file (`saves_v2.json`) with XOR-obfuscation + integrity signature, wrapped by a global `Mutex` in-memory cache and a dirty-flag for deferred flush. `save_data.rs` (1603 LOC) is the hub — it owns all save structs, the cache, disk I/O, legacy migration, and every public API for reading/writing player progress. The module is well-engineered with atomic write-rename, backup restoration, and backwards-compatible serde fields everywhere. Main technical debts are: several systems run without `run_if` guards (relying on internal early-returns instead), `VsyncMode::Adaptive` silently maps to the same `PresentMode` as `VsyncMode::On`, stale `#[allow(dead_code)]` on exported types, three stale `localStorage` doc comments, and `save_data.rs` is long enough to warrant a concern split.

### Looks Bad But Is Actually Fine

- **`save_on_exit` + `force_exit_after_save` calling `std::process::exit(0)`** — looks dangerous but is intentional and well-commented (macOS hangs for tens of seconds otherwise). The save flush happens in the preceding chained system.
- **`legacy_obfuscate` duplicating the XOR cipher from `save_encoding.rs`** — the key is different (`save_slot_{slot}` vs `unified_save_v2`), so they are genuinely distinct algorithms, not duplicated logic.
- **`migrate_very_old_progress` inlining the XOR obfuscation inline (lines 1496–1506) instead of calling `legacy_obfuscate`** — this is the same algorithm but called on a path that already has the key derivation in scope. Minor duplication but migration code is intentionally kept self-contained.
- **`GameConfig` deriving both `Resource` and `Serialize + Deserialize`** — looks like the runtime resource is being serialized directly, but the `#[serde(skip)]` annotations on all terrain/seed fields ensure the runtime-only fields are never written. The `build_config_from_game_config` helper makes the serialization path explicit.
- **`resources.rs` serde default helpers (`default_true`, `default_one`, etc.)** — these exist only because Rust's serde `default = "fn"` attribute requires free functions, not closures or literals. They are boilerplate mandated by serde, not an architectural smell.
- **`detect_window_resize` / `detect_window_move` consuming `MessageReader<WindowResized>` / `MessageReader<WindowMoved>` rather than filtering with `run_if`** — these are Bevy window events that arrive rarely. Internal `count() == 0` guard is functionally equivalent and the overhead is negligible.

### Open Questions

1. **`VsyncMode::Adaptive` intent:** Was this planned to eventually map to `FifoRelaxed` / `Mailbox` and never finished, or is the intent that "On" and "Adaptive" are treated identically on this engine version? If the latter, the variant should be removed with a serde alias migration.
2. **`saved_trees` / `saved_ponds` / `saved_bushes` / `saved_boulders` in `GameConfig`:** These four fields are `#[serde(skip)]` on `GameConfig` and are not stored in `WizardSave` directly — they are only populated via `load_level_terrain_into_config`. Is the intended lifetime that they are transient in-memory and always reloaded from `terrain_per_level`? If so, are they actually populated on game start when not in Endless mode?
3. **`resources.rs` mixing serialization DTOs and runtime Bevy resources:** `WindowConfig`, `AudioConfig`, and `ConfigFile` are serialization-only DTOs in the same file as `GameConfig` (a live `Resource`). Was there a plan to move the DTOs to a `config_file.rs`? This would clean up the module's single-file feel considerably.
4. **`progress.rs` / `SignedProgress` infrastructure:** The `ProgressData` + `SignedProgress` + `compute_signature` system in `progress.rs` is now only used by `migrate_very_old_progress` (the "very old" single-save format). Is this file kept purely for the one-time migration, or is it still in active use elsewhere? If migration-only, it could be folded into `save_migration.rs` once the split happens.

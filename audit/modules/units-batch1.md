## units-batch1

**Scope:** `src/game/units/archer/`, `src/game/units/infantry/`, `src/game/units/king/`, `src/game/units/healer/`

---

## Mental Model

These four modules cover the "classic" unit types that collectively form both the defender and attacker armies. **Infantry** is the canonical melee unit and owns two cross-cutting resources (`DefendersActivated`, `RetreatState`) that gate all other defender activation logic. **Archer** extends infantry with a ranged-only combat path (movement-delay gate + LOS checking), and features the most complex per-frame targeting logic. **King** wraps a commander aura system, provides king-cohesion flocking, manages the MP spell-shield lifecycle, and owns the guard-snap sub-system. **Healer** is a support unit that prioritises injured high-value allies, channels before firing homing bolts, and has its own VFX pipeline.

All four share the same movement boilerplate (`is_cc_immobilized → polymorphed wander → calculate_weighted_movement`) that calls into the cross-cutting `units/systems.rs` helpers. All plugins correctly use `is_gameplay_running` + an `any_exist` / `any_with_component` guard on every system batch, making most Update systems idle when no relevant entities exist or gameplay is paused.

The modules are structurally sound and well-split. The main issues are: a stale `&mut AttackTiming` in archer_ranged_combat's query (unnecessary mutable borrow), missing `is_gameplay_running` guards on two king systems, hardcoded King's Guard spawn coordinates in infantry/systems.rs that have diverged from the constant-driven King spawn, three near-identical ally-snapshot builds inside healer/systems.rs, wrong doc comments copy-pasted onto two archer functions, and minor redundant logic in arrow collision.

## Looks Bad But Is Actually Fine

- **Per-frame `Vec` snapshots in archer/combat.rs and archer/movement.rs** — `wall_snapshot`, `rock_snapshot`, `tree_snapshot` are collected twice per frame (once in `update_archer_targeting`, once in `archer_ranged_combat`). This looks redundant, but these are two separate ECS systems that cannot share query data; the snapshot pattern is the idiomatic Bevy approach to avoid aliased mutable borrows. The collections are small (walls/rocks/trees are sparse), and this is already used consistently across the codebase.
- **`archer/systems.rs` is a 5-line re-export hub** — this appears to violate the "one `systems.rs` per module max" guideline, but the file is explicitly a "re-export hub for archer systems split (Phase 18)" and performs no logic. It is intentional legacy scaffolding.
- **`is_gameplay_running` fully gates ghost-unit processing** — none of the gameplay/lifecycle/combat systems in this scope add `Without<GhostEntity>` to their queries. This is safe because `is_gameplay_running` returns `true` only on the host peer, and ghost entities only exist on the host as visual replicas; the host's simulation systems correctly process all host-side units. The ghost-gating pattern is only needed in systems that would otherwise run on the guest, which these are not.
- **`king_cohesion_force` calls `.unwrap_or(f32::MAX)`** — this is not a `.unwrap()` call; it is `min_by(...).unwrap_or(f32::MAX)` on an iterator that may be empty (no enemies alive). The fallback value semantics are correct: `f32::MAX` means "no threat", which results in minimum cohesion.
- **`healer_tick_heal_channel` uses `get_or_insert_with` for lazy snapshot building** — this is an intentional optimization: if no healer finishes its channel in a given frame, the expensive ally-snapshot collection is skipped entirely. It is good design, just verbose.
- **`HealerAttackTimer::new()` initialises `time_since_last_attack = 999.0`** — this "start at a large number" trick to allow immediate first use is a well-known pattern in this codebase (also used in `ArcherMovementTimer`). It is intentional and consistent.

## Open Questions

1. **Can the King be polymorphed?** The polymorph spell's targets query has no `Without<King>` filter. If this is intentional (King can turn into a sheep), `king_movement` needs a wander branch. If it's not intended, the polymorph system should be updated to exclude Kings.
2. **King's Guard spawn position drift (F04):** The current King's Guard spawn coordinates (`centroid_x = -1550`, `spawn_x = -1450`) don't match the King's spawn position (`WIZARD_POSITION.x = -1400`). Are guards intentionally offset from the King, or has the wizard/castle position shifted since this code was written?
3. **`healer/constants.rs:12`** — `HEALER_MOVEMENT_SPEED = 125.0` is the only movement speed in this scope that is not defined relative to `UNIT_MOVEMENT_SPEED`. Is the healer intentionally slower than infantry, and should this be expressed as a multiplier for clarity?

## game-achievements

**Scope:** `src/game/achievements/` — all seven `.rs` files.

---

### Mental model

The achievements module is a self-contained unlock engine wired entirely through Bevy Messages. It owns ~71 per-achievement Resources (each a newtype `bool` generated by `achievement_resource!`), exposes a single `AchievementsPlugin`, and splits logic across:

- `resources.rs` — resource type definitions (via macro), plus two Bevy startup systems (`init_achievements`, `reset_all_achievements`) and one run-condition helper (`achievement_locked`)
- `checks.rs` — ~49 unlock-condition systems and detection helpers (1062 LOC)
- `helpers.rs` — `do_unlock`, `unlock_and_notify_wizard_type`, and the critical `send_battle_ended` system
- `messages.rs` — 15 message types (all `#[derive(Message)]`, correctly named with `Message` suffix)
- `systems.rs` — 4-line wildcard re-export hub bridging `checks` and `helpers` into the `systems` namespace used by `plugin.rs`
- `plugin.rs` — pure registration (334 LOC); all systems have either `run_if(on_message::<…>)`, `run_if(is_gameplay_active)`, or `OnEnter(…)` guards

The module is architecturally sound. The main tech-debt concerns are: `resources.rs` housing system functions that belong in other files, `checks.rs` far exceeding the 300-LOC guideline without a strong cohesion exemption, and a repeated disk-read pattern for completionist checks.

### Looks bad but is actually fine

- **`systems.rs` wildcard re-export (`pub(crate) use super::checks::*`):** This looks like lazy `use *` abuse but is a documented "Phase 18" re-export hub pattern that lets `plugin.rs` reference all systems uniformly as `systems::check_*`. The file is intentionally minimal (4 lines).
- **`reset_all_achievements` enumerating all 71 resources explicitly:** At first glance this looks like a maintenance trap (add a new achievement and forget to add it here). However the macro pattern forces both `achievement_resource!` and manual `init!`/`insert_resource` updates in the same file, and the diff is obvious. The Rust compiler will catch missing `init_resource` registrations in `plugin.rs` but not missing entries in these lists — a real risk, but not a current bug.
- **`do_unlock` in `helpers.rs` with `pub(super)` visibility while checks.rs uses it via `use super::helpers::do_unlock`:** The visibility is narrower than `pub(crate)`, which is correct — `do_unlock` should not be callable outside the achievements module.
- **`check_roguelite_modifier_achievements` has no `achievement_locked` guard at the plugin level:** Intentional — it manages multiple resource mutability tuples internally. Each individual modifier check gates on `res.is_locked()` before calling `do_unlock`. Once all roguelite achievements unlock, the system still reads the message but exits after the `outcome != Victory` check. Acceptable.
- **`detect_spell_cast` has no `achievement_locked` guard:** Also intentional — it records `damage_types_used` for the Insight system regardless of achievement state. The achievement gating is on `check_random_magic_surge` which consumes `SpellCastMessage`.

### Open questions

1. Does `Local<bool>` in `check_shielder_encounter` / `check_assassin_encounter` / `check_aerialist_encounter` actually reset between levels? `Local` is tied to system identity, not game state — it persists for the lifetime of the app. If the player somehow starts a new session within the same process run, the latch stays true and `unlock_unit` is never called again. Is that the intended behavior?
2. For completionist achievements (`check_grand_council`, `check_walking_library`), the save is re-read from disk each time the triggering message fires. If two wizard-type unlocks happen in rapid succession (e.g. the Grand Council fires twice), does the second read see the state written by the first unlock? Are save writes synchronous enough to guarantee this?
3. `check_roguelite_modifier_achievements` checks `current_level.0 != ROGUELITE_MAX_LEVEL` as a gate for roguelite completion achievements. If the roguelite max level changes, this constant must be updated. Is `ROGUELITE_MAX_LEVEL` validated anywhere against the actual level table?

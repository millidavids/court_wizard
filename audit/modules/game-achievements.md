## game-achievements

**Scope**: `src/game/achievements/` — all `.rs` files (17 files, ~2116 LOC)

---

### Mental model

The achievements module is a self-contained, event-driven unlock system. It defines ~65 per-achievement Bevy `Resource` types (each a `bool` newtype) generated by the `achievement_resource!` macro. At startup, `init_achievements` hydrates all resources from the save cache. Every achievement check system is gated by `run_if(on_message::<...>)` or `run_if(is_gameplay_active)` plus `run_if(achievement_locked::<T>)`, which means zero continuous per-frame cost once an achievement fires. The `BattleEndedMessage` snapshot pattern centralises all battle-outcome data so check systems remain stateless. The module was recently refactored from a monolithic `checks.rs` into feature-sliced sub-files; the split is largely clean but leaves system bodies (`reset_all_achievements`, `init_achievements`) living inside the `resources/` subtree, and the roguelite modifier resource names break the naming convention used everywhere else.

### Looks bad but is actually fine

- **`reset_all_achievements` ignores `_msg` without reading it** — the `run_if(on_message::<ClearProgressMessage>)` guard in the plugin already gates execution; the message content is irrelevant, so prefixing with `_` and not consuming it is correct.
- **`check_roguelite_modifier_achievements` has no outer `achievement_locked` guard** — it checks `.is_locked()` internally for each of 16 achievements before calling `do_unlock`. It fires at most once per battle end via `on_message`, so the cost is negligible. A single consolidated system is cleaner than 16 separately-gated ones.
- **`detect_spell_cast` has no `achievement_locked` gate** — it serves a dual purpose: it fires `SpellCastMessage` for achievement detection AND populates `BattleInsightData.damage_types_used` for the wizard tower study UI. Correctly cannot be gated behind a single achievement's lock.
- **`grant_achievement_insight` absent for many `do_unlock` calls** — intentional: `AchievementId::insight_reward()` returns `0` for those achievements, making the call a no-op. Omitting it is correct, not a missing call.
- **`encounter_system!` macro causes two save-cache writes on unlock** — `unlock_unit` + `unlock_achievement` both write to the in-memory cache on the same frame. Both are idempotent and go only to the in-memory cache (no synchronous disk I/O). The `achievement_locked` gate prevents re-triggering.
- **`init_achievements` uses a nested `macro_rules! init!`** — a local macro inside a function body is unusual but valid Rust; it cleanly eliminates 65 near-identical lines without leaking the macro into module scope.
- **Ghost entity concerns for encounter and boss-seen systems** — `is_gameplay_active` restricts all gameplay achievement systems to the multiplayer host. Ghost entities (`GhostEntity`) are spawned only on the guest side via `apply_state_snapshot`. The host has no `GhostEntity` components, so `Without<GhostEntity>` guards are not needed here.
- **`load_unified_save()` called inside event-triggered systems** — the static `SAVE_CACHE` mutex means this is an in-memory clone (no disk I/O) after first load. The mutex lock + clone is acceptable for once-per-event triggering.

### Open questions

1. Should `BossesSeenThisBattle` live in `resources/progress.rs` alongside persistent unlock flags, or in `resources/tracking.rs` alongside other transient battle-scoped state? It is semantically a tracker, not a progress flag.
2. Does `WizardType::all()` allocate a `Vec` on every call? If so, `check_grand_council` allocates on every `WizardTypeUnlockedMessage`. A `const` count would be cleaner.
3. `detect_stormbringer` runs an O(rods × squalls) nested loop every gameplay frame until the Stormbringer achievement fires. In practice there are at most a few rods and one squall, so this is not a real concern — but it is worth a comment explaining the expected small bounds.

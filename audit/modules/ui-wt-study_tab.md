## ui-wt-study_tab

**Scope:** `src/ui/wizard_tower/study_tab/` — three files, 3,380 LOC total. The two code files are the two largest in the repo (interaction.rs: 1,969 LOC; panels.rs: 1,403 LOC).

---

### Mental model

The study tab is a dual-panel "spell research and talent" screen sitting inside the Wizard Tower meta-game hub. The right panel renders a zoomable/pannable spell-web graph (circular nodes for each learnable spell plus an "insight bonus constellation") on a procedural starry-sky background. The left panel is a dynamic detail card that rebuilds itself whenever the player selects a node, showing description, a progress+allocation slider, talent tier cards, and a Commit button.

The module splits naturally into two concerns that match the file names: **panels.rs** handles spawn/rebuild of all UI entities (graph, edges, nodes, sliders, constellations, HUD overlays) plus graph pan/zoom/animation logic; **interaction.rs** handles real-time system callbacks (slider drag, talent hover/click, allocation text refresh, the gamepad cursor subsystem, and the detail panel rebuild driven by resource changes). Components and resources live in the sibling `components.rs` (not in scope but readable for context). System registration is entirely in `plugin.rs`, which applies tight `run_if` guards on every system set.

Key runtime contract: `InsightAllocation`, `SelectedStudySpell`, `SelectedInsightBonus`, and `GraphViewState` are inserted/removed as a group on Study tab enter/exit; all study systems are gated on `resource_exists::<SelectedStudySpell>`.

### Looks bad but is actually fine

- **Multiple `load_unified_save()` calls per frame** — the function uses an in-memory mutex-guarded cache (save_data.rs:559-582), so no disk I/O occurs after the first call. The redundancy is suboptimal (F1) but not the disk-thrash it looks like.
- **`handle_detail_slider_interaction` double-loop on `just_pressed`** — lines 844–864 have two separate `just_pressed` loops (one on tracks, one on handles). This is intentional: the first loop starts dragging when the cursor is over the track but not directly on the handle; the second loop starts dragging when the handle itself is pressed. Not a bug.
- **`cleanup_study_cursor_on_area_removed` unconditional `Update`** — explained in plugin.rs comment: must fire even outside WizardTower state to clear `FocusNavInhibit` when the wizard tower is exited entirely. The `RemovedComponents` check inside is cheap (O(1) when nothing was removed).
- **`update_study_detail_panel` and `update_insight_detail_panel` checking `!is_changed()` internally** — even though these systems run on every frame inside the study-tab system set, both have early-return guards on their respective resources. The group-level `run_if(resource_exists::<SelectedStudySpell>)` is the outer gate; the inner `is_changed()` guards are a second layer. This is correct, not redundant.
- **`format!("{:?}", spell)` used as string keys** — looks fragile, but this is the project-wide pattern established in save_data.rs for spell serialization. Changing it would break existing saves (backwards compat requirement). Consistent usage across the codebase is by design.
- **Large `spawn_study_panels` function (~480 LOC) with deeply nested closures** — the function is one long declarative UI build tree, not a god function with branching logic. The size is structural (Bevy child-spawner closures), similar to an asset registry exemption. Splitting it would require passing context across function boundaries and is not clearly better.

### Open questions

1. Is `update_study_cursor` (line 1451) using the LEFT stick intentionally for cursor movement, or was it supposed to use the right stick? The doc comment (F3) says "right stick" but the code uses left. If left is correct, does the left stick drive BOTH cursor movement AND edge-scroll simultaneously while in cursor mode? That would make edge-scroll redundant with cursor movement.
2. `TalentProgressBarFill.spell` (F7) — was a reactive talent-bar update system planned and never built? If so, either build it or strip the field.
3. After a `rebuild_study_ui` with `preserve_selection = true`, `SelectedStudySpell.set_changed()` is called explicitly (panels.rs:337–339) to force `update_study_detail_panel` to re-render. Could this leave a one-frame gap where the left panel shows stale content while the new right-panel entities are still being spawned by deferred commands?

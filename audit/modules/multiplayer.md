## multiplayer

**Scope:** `src/game/multiplayer/` — all 16 `.rs` files (9,251 LOC total)

---

### Mental model

The multiplayer module owns the entire networking lifecycle for both versus and co-op modes. The host runs the full single-player simulation (movement, combat, spells) and snapshots it to the guest every frame over an unreliable channel. The guest renders ghost entities from those snapshots and forwards its own spell hits/status effects back to the host via reliable messages. A CRDT layer reconciles bidirectional HP changes so guest-cast spells have authoritative effect on host units without per-spell round-trips.

The module is split into well-named concern files (`host_systems`, `guest_snapshot`, `spell_sync`, `loading`, `coop`, `coop_pause`, `crdt_sync`, `score_stats`, `spawning`, `guest_visuals`, `excremage_theming`) but several of them are large enough to warrant further decomposition. Ghost-gating (the primary MP risk class) is sound for gameplay systems: ghost-effect entities carry `GhostSpellEffect`, ghost units carry `GhostEntity`, and the SP gameplay systems in `units/` that could double-apply are all documented to use `Without<GhostEntity>`/`Without<GhostSpellEffect>` filters. The CRDT attachment system (`attach_crdt_health`) intentionally runs on ghost units — that is by design and correct.

The one structural gap is `plugin.rs` at 552 LOC: it is pure registration (no system bodies) and therefore is not a purity violation, but its readability is strained by inline local variable aliases for run conditions and dense chained ordering constraints. The code is correct; the concern is navigability.

### Looks bad but is actually fine

- **`attach_crdt_health` has no ghost filter**: Ghost units need `CrdtHealth` so that `sync_health_to_crdt` can record guest-applied damage into the CRDT pipeline. Intentional and correct.
- **`forward_status_effects_to_host` polls rather than using `Added<>`**: The comment explains this — `Commands`-queued inserts are not visible to `Added<>` until after the next flush. Polling with `Without<StatusEffectForwarded<T>>` is the correct workaround.
- **`in_mp_running` returns true for Paused, SpellBook, and CauldronMenu**: "Running" in this context means "gameplay active, not at score screen or disconnected." Systems gated on it should fire through menu overlays. Counterintuitive name but intentional semantics.
- **`detect_mp_disconnect` handles both `Failed` AND `Disconnected` states**: The comment (systems.rs:706-710) explains that `ConnectionState::Disconnected` represents a peer-initiated graceful close. Without this a graceful remote close would silently strand the player in a live match.
- **13 separate `cleanup_forwarded_marker::<T>` registrations in plugin.rs**: This is the correct Bevy pattern for generic marker cleanup — there is no way to iterate over a set of component types at runtime, so one registration per type is necessary.
- **`MpSpawnQueue` bulk-processing all tasks per frame with a deferred-state guard**: The `needs_command_flush` / `creates_deferred_state` pattern is the correct workaround for Bevy's deferred resource visibility. No issue.
- **`apply_state_snapshot` and `send_crdt_snapshot` both operating on GhostEntities in the same frame**: These are chained (`.chain()` in plugin.rs:325-339), so the order is deterministic. The bidirectional operation within one frame is intentional.

### Open questions

1. `apply_status_to_entity` line 691: the Polymorph failure path inserts `SleepModifier` as a fallback when `polymorph_capture` is `None`. Is this intentional? If a unit is already polymorphed (the `Without<PolymorphedModifier>` filter on `polymorph_targets` returns `None`), silently sleeping it instead of no-op-ing could create subtle gameplay inconsistencies.

2. The `receive_spell_visual_snapshot` and `receive_crdt_snapshot` both drain `incoming_unreliable` and re-queue the other type's packets. Both run in the same `Update` frame. Is there a scheduling guarantee that they don't both drain the same packet? (They should be fine since they filter on different type-prefix bytes, but the ordering is implicit.)

3. `coop_pause_heartbeat` runs with `run_if(coop_sync_pause_enabled)` which checks for a live `MultiplayerSession`. Is there a risk of it firing for one frame after `cleanup_mp_game` removes the session but before the run condition is re-evaluated? An extra heartbeat on exit is harmless but worth confirming.
